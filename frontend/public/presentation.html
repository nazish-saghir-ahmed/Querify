The Core Failure Mode

Why Standard Text-to-SQL Fails in Enterprise

The fundamental flaw in modern LLM query generation is not syntax — it is unaddressed semantic ambiguity.

01

The Guesswork Trap

When a stakeholder asks "Show me the best performing companies", standard bots randomly pick top-line revenue, net profit, growth rate, or benchmark scores without confirming user intent.

02

Silent Hallucination

LLMs generate syntactically convincing SQL that queries the wrong columns, produces misleading numbers, and passes quietly into boardroom presentations with zero warning.

03

Execution Vulnerabilities

Most prototypes send raw AI-generated text straight to database connections with weak regex checks, allowing destructive mutation attacks (DROP, DELETE, ALTER) or query chaining.

Prompt: "Show the best performing AI companies in 2024" Result without Clarification: 4 Different Executives get 4 Conflicting Answers
The Breakthrough

The Querify Paradigm: Proactive Intent Alignment

Treating ambiguity as a first-class citizen through human-in-the-loop clarification before code synthesis.

Step 1: Ambiguity Detection

Natural Language Lexical & Semantic Scanner

Queries are scanned for underspecified qualifiers (e.g. "best", "top", "made most money", "success"). If found, query generation intentionally pauses.

Step 2: Structured Clarification Dialogue

Keyboard-Navigable Disambiguation Cards

The engine synthesizes discrete business metrics (e.g. Gross Revenue vs Net Profit vs YoY Growth vs ROI) and prompts the user to select.

Step 3: AST Verification & Visualization

Guaranteed Read-Only SQL Compilation

The clarified intent is compiled into verified SELECT SQL, checked by JSqlParser, and plotted into interactive Bar/Line/Pie charts.

Security Engineering

AST-Level Security vs. Regex Blacklisting

Why traditional string matching fails and how Querify guarantees 100% read-only operations.

Traditional Regex / String Filter

Vulnerable
  • // Bypassed by comments & casing:
    DrOp/**/TaBLe companies;
  • // Bypassed by statement chaining:
    SELECT * FROM companies; DELETE FROM...
  • // Bypassed by encoded injection strings

Querify JSqlParser AST Guard

Deterministic
1. Root Node Verification:
statement instanceof Select.class == true
2. Statement Chaining Scanner:
Normalizes single trailing ; and rejects multiple statements.
3. Table Extraction Whitelist:
Extracted table names must strictly match approved domain tables.
4. Execution Bounds:
Automatic LIMIT 100 injection with 5-second timeout.

Viva Voce Defense

Anticipated Technical Questions & Defense

Rigorous architectural justifications for evaluator inquiries.

Q1. Why use Java/Spring Boot instead of simple Python/Flask?

Defense: Enterprise scalability and strict typing. Spring Boot offers HikariCP connection pooling, JdbcTemplate bounds, and direct integration with JSqlParser for AST evaluation without inter-process overhead.

Q2. How do you prevent LLMs from hallucinating table or column names?

Defense: Schema Grounding. System prompts inject exact DDL schemas, primary/foreign keys, and units. Any generated query referencing an unauthorized table is rejected by AST whitelist validation.

Q3. Why is regex insufficient for SQL injection prevention?

Defense: Regex operates on raw lexical characters and can be bypassed with inline comments, whitespace variations, and multi-statement chaining. JSqlParser analyzes the parsed syntactic structure of the query.

Q4. What happens if the external AI API is down or rate-limited?

Defense: Querify features a built-in deterministic rule engine and in-memory H2 database fallback. The system transitions into Demo Mode without dropping connections or crashing.
